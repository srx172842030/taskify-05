# Taskify 项目章程

## 核心原则

### I. 代码质量优先

- 每一次变更必须可读、自文档化，且不含死代码、重复代码与不可达分支。
- 所有代码在合并前必须通过静态分析（代码风格检查、格式化，以及适用的类型检查）。
- 复杂度必须有据可依：抽象仅在确实消除重复或澄清意图时引入，绝不臆测性地引入。
- 命名必须表达意图；注释解释「为什么」，而非「是什么」。

**理由**：可维护、可读的代码是其他一切原则赖以成立的基石——不可测试、不可读的代码会让正确性、一致性与性能都无从维系。

### II. 测试标准（不可协商）

- 所有新行为都必须有测试；默认采用「测试先行」循环——先写失败的测试，再实现使其通过，最后重构（红-绿-重构）。
- 每个缺陷修复都必须附带一个回归测试：修复前复现失败，修复后通过。
- 单元测试必须覆盖逻辑与边界情况；集成测试必须覆盖契约边界（接口、共享 schema、服务间通信）；端到端测试必须覆盖关键用户旅程。
- CI 必须强制执行最低行覆盖率与分支覆盖率门槛（默认 80%）；降低门槛必须提交书面例外并经评审批准。
- 测试必须是确定性的、彼此隔离的，且快到足以在每次变更时运行。

**理由**：测试是正确行为的可执行规范，也是允许自信变更的安全网；未测试的代码视为未完成的工作。

### III. 用户体验一致性

- 所有界面必须基于共享设计系统（组件、设计令牌、间距、排版）构建；禁止一次性样式与游离模式。
- 每个界面都必须可访问：语义化标记、键盘可导航、足够的颜色对比度、兼容屏幕阅读器（以 WCAG AA 为基线）。
- 交互模式、术语与视觉语言必须在整个产品中保持一致；设计变更先在共享组件上完成，绝不只改单一屏幕。
- 布局必须适配手机宽度，且不得引入横向滚动。

**理由**：一致性降低用户的认知负担，也降低开发者的维护成本；可访问性是基线要求，而非增强项。

### IV. 性能要求

- 每个功能在实现前都必须声明性能预算（如首屏加载时间、包体积或响应延迟）。
- 变更必须据此预算在变更前后度量性能影响，且未经明确批准不得回归超出声明的阈值。
- 优化必须只针对已度量的瓶颈；禁止过早优化，未度量的「优化」视为臆测性变更。

**理由**：性能是一项功能，也是一种质量属性；预算让它可度量，从而防止无声的、不断累积的回归。

### V. 简洁性与可维护性

- 优先采用满足需求的最简方案（YAGNI）；在确有需要之前，推迟引入复杂度。
- 优先采用标准、广为人知的模式与「朴素」技术，而非耍小聪明。
- 每新增一个依赖都必须有依据并经评审；在引入库之前，优先使用平台或现有技术栈。

**理由**：每一行代码与每一个依赖都是长期负债；简洁性是让代码库可变更、其性能与质量可测试的关键。

### VI. 文档中文化

- 所有项目文档必须使用中文撰写：规格说明、实施计划、任务清单、README、代码注释、提交信息与接口文档。
- 技术标识符、代码，以及没有公认中文译名的术语（如框架名、接口名）可保留原文，但对其的说明必须使用中文。
- 面向用户的文案必须使用中文；面向开发者的文档与注释同样必须使用中文。

**理由**：统一使用单一语言可减少歧义与团队上手成本；单一语言的文档才便于评审与长期维护。

## 技术标准

- 安全：绝不提交任何密钥；在信任边界处必须校验输入；所有集成与访问控制遵循最小权限原则。
- 可访问性：WCAG AA 是所有面向用户界面的强制基线。
- 工具链：项目的代码风格、格式化与类型检查配置为权威标准；本地构建必须与 CI 一致。
- 文档：非显而易见的行为必须与其实现代码一并文档化。

## 开发工作流与质量门禁

- 所有变更都必须经过评审；仅当 CI 通过且获得至少一名维护者批准后，变更方可合并。
- CI 必须在合并前通过代码风格检查、格式化、类型检查与完整测试套件；任何一项失败即阻断变更。
- 「完成的定义」包括：新增或更新测试、无新增告警或错误、更新相关文档、对照既定目标验证变更。

## 治理

- 本章程凌驾于其他所有实践与惯例之上；发生冲突时以本章程为准，并修正冲突的实践。
- 技术决策与实现选择必须对照这些原则进行评估：当多个方案同样可行时，选择与本章程最一致者，并记录所权衡的取舍。
- 对任何原则的偏离都必须显式、书面并经过评审批准；偏离是例外，而非沉默的先例。
- 修订必须以书面形式提出并附理由，经评审后按语义化版本规则定版：MAJOR 表示不兼容地删除或重新定义原则，MINOR 表示新增或实质性扩展指导，PATCH 表示澄清与措辞修正。
- 合规性在每次评审中检查：评审者必须核验变更是否符合本章程，并在批准前标记违规项。
