# 研究报告：Taskify 核心协作功能

本文档记录 Phase 0 的技术决策与取舍，供 `data-model.md`、`contracts/` 与后续实现参考。

## 1. 看板拖拽库：vue-draggable-plus（用户指定）

- **决策**：前端看板拖拽使用 `vue-draggable-plus`。
- **理由**：用户明确指令；它是基于 Sortable.js 的 Vue 3 拖拽库，提供 `VueDraggable` 组件与 `group` 跨列拖拽能力，成熟且与现有 Vue 3 + TS 技术栈兼容。
- **备选**：`vuedraggable`（Vue 2 时代产物，Vue 3 支持有限）、`@formkit/drag-and-drop`、自研指针事件拖拽。均不如 `vue-draggable-plus` 契合 Vue 3 且现成。

## 2. 拖拽与「相邻列」约束的结合

- **决策**：桌面看板用 `VueDraggable` 实现四列间拖拽；拖放「落下」时**不直接提交**，而是由前端先将「目标列」交给后端校验，后端仅在目标列为当前列的相邻列时放行，否则拒绝并回滚到原列。
- **理由**：规格澄清（Q1）要求「仅限相邻列，不可跨列」。拖拽库本身允许自由拖到任意列，故需在提交环节用服务端权威校验兜底（前端仅做体验层提示），确保约束不被绕过。
- **实现要点**：`taskify-project` 提供 `POST /tasks/{id}/move`，`toStatus` 与当前 `status` 必须相邻（TODO↔IN_PROGRESS↔IN_REVIEW↔DONE），否则返回 `PARAM_ERROR`。前端拖放失败时把卡片动画回原位并提示。

## 3. 移动端任务移动的替代交互（无拖拽）

- **决策**：手机宽度下看板为「单列 + 列切换器」（规格 Q3），拖拽在触屏上不可用；任务移动改为在**任务详情抽屉内**提供「移动到上一列/下一列」按钮（相邻列），复用同一 `move` 接口。
- **理由**：满足章程「无横向滚动」与触屏可用性；`vue-draggable-plus` 仅作为桌面增强，移动端走确定性按钮。
- **备选**：触屏长按拖拽（体验差、易误触）、下拉菜单选列（交互多一步）。按钮最直接、可访问性好。

## 4. 实时通知传输方式：SSE（而非 WebSocket）

- **决策**：通知实时推送采用 **SSE（Server-Sent Events）**，前端经 `EventSource` 连接 `GET /api/v1/notifications/stream` 接收；通知服务以 Spring WebFlux `text/event-stream` 单向推送。
- **理由**：通知为**纯单向**（服务端→客户端），SSE 用普通 HTTP、经网关路由简单、原生自动重连、可复用 JWT 鉴权头，比 WebSocket 更简（契合原则 V）。网关（WebFlux）对 SSE 天然友好。
- **备选**：WebSocket/STOMP（双向能力冗余、网关与连接管理更重）、长轮询（延迟与开销大、不「实时」）。均被否。

## 5. 事件流转：RocketMQ

- **决策**：`taskify-project` 在任务**创建、修改、看板移动**时发布领域事件到 RocketMQ topic（如 `taskify-task-events`）；`taskify-notification` 消费事件，计算接收者、落库通知并通过 SSE 推给在线接收者。
- **理由**：001 已引入 RocketMQ 作为异步通信底座；跨服务（project → notification）用消息解耦，project 服务不阻塞在通知投递上，符合「实时且 <3s」的松耦合要求。
- **事件类型**：`TASK_CREATED`、`TASK_UPDATED`、`KANBAN_MOVED`。评论**不**触发通知（规格未要求）。

## 6. 微服务拆分：taskify-project + taskify-notification

- **决策**：新增两个服务——`taskify-project`（项目、任务、评论、看板移动）与 `taskify-notification`（通知持久化、未读计数、SSE 推送）。
- **理由**：项目/任务/评论/看板是强关联聚合（任务属于项目、评论附属于任务、看板是任务的视图），放在同一服务内避免跨服务 join 与分布式事务；通知是独立关注点（有自己的持久化与实时通道），单独成服务以隔离推送负载。
- **备选**：更细拆分（project 与 task 分两服务，或 comment 独立）会引入不必要的跨服务查询与一致性复杂度，对 5 用户/3 项目的阶段一过度设计；单体则违背微服务方向。

## 7. 看板列的建模：任务状态枚举（非独立列实体）

- **决策**：看板四列建模为任务上的**状态枚举字段** `status`（`TODO`/`IN_PROGRESS`/`IN_REVIEW`/`DONE`），列即「按 status 分组展示」；不建独立列表。
- **理由**：列固定且有序、任务恰好属于一列（规格 FR-012），枚举字段天然满足「恰好属于四列之一」；「相邻列」即枚举顺序上的相邻。无需列实体与列排序。
- **相邻关系**：`TODO ↔ IN_PROGRESS ↔ IN_REVIEW ↔ DONE`。

## 8. 通知接收者规则

- **决策**：任务创建/修改 → 通知任务**负责人**（`assignee_id` 非空时）；看板移动 → 通知负责人 + 任务**创建者**；负责人为空时，创建/修改不产生负责人通知（看板移动仍通知创建者）。
- **理由**：与规格「相关负责人」及澄清 Q3（负责人可留空）一致。
- **去重**：同一事件若负责人=创建者，仅产生一条通知。

## 9. 前端状态与实时同步

- **决策**：Pinia stores 管理 `projects`/`tasks`/`notifications`；看板与通知通过 SSE 增量更新，移动后本地乐观更新并以后端响应为准回滚。
- **理由**：001 已有 `stores/` 目录与 Pinia 约定；SSE 连接封装为 `useNotifications` 组合式函数，未读角标由未读计数接口 + SSE 事件联动。

## 10. 预置数据与访问模型

- **决策**：阶段一**不建模项目成员表**；5 名预置用户（1 产品经理、4 工程师）可访问全部 3 个示例项目（访问模型默认「全团队可访问所有项目」）。预置数据经 Flyway 迁移（或种子脚本）初始化。
- **理由**：规格澄清阶段已将该访问模型作为默认假设；5 人/3 项目的规模下无需成员关系表，避免过早引入复杂权限。
- **备注**：项目实体仍记录 `created_by`（创建者），用于通知「创建者」与未来扩展成员关系。

## 11. 任务详情抽屉与评论权限

- **决策**：任务详情以**侧边抽屉**呈现（规格 Q2）；评论的编辑/删除仅限**作者本人**（规格 Q2/澄清），后端在 `PATCH/DELETE /comments/{id}` 上校验 `author_id == 当前用户`，否则 `FORBIDDEN`。
- **理由**：规格已明确；后端权威校验兜底前端展示。

## 12. 移动端看板呈现

- **决策**：手机宽度下看板单列展示 + 列切换器（规格 Q3），不横向滚动。
- **理由**：满足章程「无横向滚动」硬性要求；用 Tailwind 断点实现，复用 001 响应式约定。
