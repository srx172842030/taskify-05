# 研究：Taskify 任务时间与依赖关系

本文档记录 003 功能的关键技术决策与备选方案。技术栈沿用 001/002（Java 21 + Spring Boot 3.5.x 微服务、Vue 3 + TypeScript、PostgreSQL + Flyway、RocketMQ、SSE），此处不重复调研，仅覆盖本功能引入的新决策点。

## 决策 1：开始/截止时间的存储表示（含「全天」）

- **决策**：在 `taskify_task` 增加 `start_at`、`due_at`（`TIMESTAMPTZ`，可空）与 `start_all_day`、`due_all_day`（`BOOLEAN`，默认 false）。全天任务以「当地日期 + 00:00」存储日期部分，界面仅展示日期；具体时刻存储完整时间戳。
- **理由**：单一时间戳 + 布尔「全天」标记最简，避免双类型列；`TIMESTAMPTZ` 与既有 `created_at`/`updated_at`（`OffsetDateTime`）一致；全天用午夜锚点，使「截止不早于开始」在两种形态下都能按日期比较。
- **备选**：分别用 `DATE` 与 `TIMESTAMP` 两列存储。被否——引入冗余列与两套比较/展示逻辑，复杂化。

## 决策 2：时区处理

- **决策**：单一时区（阶段一约定 UTC 存储、界面按统一本地时区展示），不处理多时区与夏令时边界。
- **理由**：规格「假设」明确单一时区；团队规模小（5 人），v1 无需按用户时区差异化。
- **备选**：按用户偏好时区存储与展示。被否——需引入用户时区偏好设置，超出范围。

## 决策 3：提醒节点两种形态的建模与解析

- **决策**：新增 `taskify_reminder` 表，`mode ∈ {ABSOLUTE, RELATIVE}`。`ABSOLUTE` 存 `trigger_at`；`RELATIVE` 存 `offset_minutes`（>0，表示「提前」）+ `anchor ∈ {START, DUE}`。相对提醒的「实际触发时间」在扫描时按锚定时间减去偏移动态解析；锚定时间字段（开始/截止）未设置时无法解析，不触发，配置界面提前提示。
- **理由**：绝对与相对统一到一张表，用可空字段区分，校验集中在服务层；相对提醒在运行时解析，能始终反映任务排期的最新变化。
- **备选**：创建相对提醒时直接「落成绝对时间」。被否——任务开始/截止时间之后被修改时，预计算的绝对时间会失同步，无法反映最新排期。

## 决策 4：提醒的触发调度机制

- **决策**：在 `taskify-project` 内用 Spring `@Scheduled` 周期任务扫描 `fired = false` 且「解析触发时间 ≤ now」的提醒，置 `fired = true` 后发布 `REMINDER_DUE` 事件到 RocketMQ；`taskify-notification` 消费后生成 `REMINDER` 通知并 SSE 推送。扫描周期须 ≤ 1s，以满足 SC-003「提醒到达后 3 秒内送达」。
- **理由**：相对提醒的触发时间随任务时间变化，需动态解析，周期扫描最可靠；RocketMQ 延迟消息的延迟等级粒度固定、不适合任意时刻；扫描（≤1s）+ SSE 即时推送 + 持久化列表兜底，可满足「<3s 送达」的规格目标。
- **备选**：RocketMQ 延迟消息、Quartz 动态任务、独立调度服务。被否——延迟等级粗粒度、动态任务生命周期管理复杂、独立调度服务超出本功能规模。

## 决策 5：阻塞关系建模与「完成」判定

- **决策**：新增 `taskify_task_dependency`（`blocker_id` 被依赖/阻塞者、`dependent_id` 依赖/被阻塞者）。「完成」= `status = DONE`（复用既有看板状态机，不新增完成标志）。任务「被阻塞」= 存在至少一个 `blocker` 其 `status != DONE`。
- **理由**：与规格澄清一致（同项目、硬阻塞）；「完成」复用唯一状态源，避免第二套完成语义失同步。
- **备选**：新增显式 `completed` 标志或 `done_at` 时间戳。被否——与看板列重复，易失同步。

## 决策 6：硬阻塞的强制点与「不可开始」的计算

- **决策**：硬阻塞在「开始」动作上强制——`POST /tasks/{taskId}/move` 当目标为 `IN_PROGRESS` 且任务被阻塞时拒绝，返回新错误码 `TASK_BLOCKED`。「被阻塞」为读时计算（查询时联查未完成的 blocker），不在任务表落布尔列。
- **理由**：把硬约束收敛到唯一入口（开始动作），避免状态列漂移；读时计算保证与阻塞关系实时一致。
- **备选**：在 `taskify_task` 维护 `blocked` 布尔列随阻塞关系/状态变化双写。被否——双写易失同步，需额外事务维护，违反简洁性（章程 V）。

## 决策 7：阻塞状态变化事件与通知

- **决策**：阻塞状态变化（阻塞/解除）由 `taskify-project` 在「任务移动（进/出 DONE）」「阻塞关系创建/删除」时计算受影响任务，发布 `TASK_BLOCKED`/`TASK_UNBLOCKED` 事件；通知服务新增 `TASK_BLOCKED`/`TASK_UNBLOCKED`/`REMINDER` 通知类型。复用既有 RocketMQ 事件 → 通知落库 → SSE 推送链路。
- **理由**：复用既有事件解耦模式，不引入新通知通道。
- **备选**：阻塞状态变化走 OpenFeign 直调通知服务。被否——破坏既有事件解耦模式，引入服务间同步耦合。

## 决策 8：循环依赖与自依赖防护

- **决策**：建立阻塞关系时应用层校验：`blocker_id != dependent_id`；新增关系不形成环（沿 `blocker` 方向做 DFS/拓扑检查）；两任务须同项目。违反则 `PARAM_ERROR`。
- **理由**：规格 FR-006/FR-008 要求；在写入前拦截环，能给出友好错误；同项目约束避免跨项目耦合。
- **备选**：仅数据库唯一约束 + 事后检测。被否——无法在创建时拦截环。

## 决策 9：界面表达（不引入日历视图）

- **决策**：时间字段、全天标记与「不可开始」状态在任务卡片、任务列表、任务详情抽屉三处一致展示；不新增日历/时间轴视图；阻塞警示以徽标 + 文案列出阻塞任务，并在任务详情抽屉中给出解释。
- **理由**：规格明确「不引入日历视图」，排期与依赖信息在现有视图内表达。
- **备选**：新增日历/甘特视图。被否——超出规格范围。

## 决策 10：全天/相对提醒的边界语义

- **决策**：全天任务的开始时间按当日 00:00、截止时间按当日 23:59:59 参与比较与相对提醒解析；相对提醒仅支持「提前」（`offset_minutes > 0`，即开始/截止之前），不支持「延后」；提醒节点可为任意未来时间点，不与开始/截止时间强制先后约束。
- **理由**：符合「提前量」措辞与常见习惯；简化 v1 语义。
- **备选**：支持「延后」偏移或强制提醒须早于截止。被否——超出描述范围或过度约束。
