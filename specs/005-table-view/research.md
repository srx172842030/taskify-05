# 研究：表格视图与视图级筛选/分组/排序（第二视图）

本文件记录 Phase 0 的技术决策与理由，全部"待澄清"项在此解决。

## 决策 1：优先级字段的表示与取值

- **决策**：`taskify_task` 新增可空 `priority VARCHAR(8)` 列，枚举 `HIGH`/`MEDIUM`/`LOW`，`NULL`＝未设置。前端以中文标签「高 / 中 / 低」展示，未设置显示「无优先级」。默认新任务不设优先级（保持既有创建流程不变）。
- **理由**：满足"按优先级"泳道、筛选、排序与批量编辑；可空设计不破坏既有任务与既有创建/修改接口的兼容性（旧请求不含 priority 时保持不变）。三档是团队任务管理的最小可负担分级，避免过度设计。
- **备选**：更细粒度（如 1–5 星或 P0–P4）被否——需求未要求，且增加 UI 与排序复杂度；复用既有"状态"列临时替代被否——语义错位、无法持久表达优先级。

## 决策 2：批量编辑接口设计

- **决策**：新增单个端点 `POST /api/v1/projects/{projectId}/tasks/batch-update`，请求体 `{ taskIds: string[], patch: { assigneeId?, priority?, startAt?, startAllDay?, dueAt?, dueAllDay?, status? } }`。服务端在单事务内逐条复用既有校验（时间合法性、相邻列、硬阻塞），任一任务校验失败则整体回滚，返回 `PARAM_ERROR` 或 `TASK_BLOCKED`（附失败原因）；全部成功返回更新后的任务数组。
- **理由**：满足 FR-008（一次应用、仅影响选中任务）与 FR-009（整体拒绝、不产生部分生效）；单请求原子性天然满足性能预算，避免 N 次逐条请求。校验复用 `TaskService.update`/`move` 既有规则，避免复制逻辑（章程 I/VII）。
- **备选**：前端并发 PATCH 被否——无法保证原子回滚，且会产生"部分成功"；后端提供"尽力而为"批量（返回部分失败列表）被否——与 FR-009"整体拒绝"相悖。
- **状态字段语义**：批量设置 `status` 视为"移动每个选中任务到目标列"，逐任务校验相邻列与硬阻塞；若任一任务不满足（如跨列、被阻塞），整批拒绝。前端工具条据此提示合法目标。

## 决策 3：跨用户实时同步机制

- **决策**：扩展现有 SSE 通知通道——前端在收到 `TASK_CREATED`/`TASK_UPDATED`/`KANBAN_MOVED`（及既有 `TASK_BLOCKED`/`TASK_UNBLOCKED`）通知时，刷新**当前项目**任务列表（复用 `useTasks().reload()`）。
- **理由**：满足 FR-011（任一视图修改经既有实时机制同步给其他在线用户）。当前实现仅对阻塞事件刷新任务，其余任务变更只产生通知、不刷新看板/列表，存在同步缺口。扩展通知处理器而非新建通道，遵循简洁性与"不改变既有通知行为"（通知本身仍照常展示）。
- **备选**：新建独立 WebSocket 任务同步通道被否——重复造轮子，违背简洁性；保持现状（仅通知）被否——不满足 FR-011 的"视图同步"。

## 决策 4：视图配置持久化

- **决策**：视图配置（筛选条件、分组字段、排序字段与方向）存于浏览器 `localStorage`，键形如 `taskify:view:{projectId}:{view}`，按用户浏览器隔离（当前为单用户会话，天然个人级）。以 `useViewConfig(projectId, view)` 封装读写与默认值。
- **理由**：满足 FR-016/FR-017（按用户持久化、可清除）。个人偏好无需跨端同步，`localStorage` 是最简实现，符合章程 V（YAGNI）。不新增后端表/接口/迁移。
- **备选**：后端持久化被否——需新增表、接口与鉴权，超出个人偏好需求；`sessionStorage` 被否——不满足"下次访问恢复"（仅当前会话）。

## 决策 5：筛选/分组/排序语义

- **决策**：作为前端纯函数（`useTaskQuery`）作用于共享 `tasks` 数组，三者按"先筛选 → 再分组 → 组内排序"叠加：
  - **筛选**：条件集（"只看我的任务"＝`assigneeId === 当前用户`；另可叠加状态、负责人、优先级、有无截止日等）。
  - **分组**：按负责人或优先级（或不分组的平铺模式）；未分配负责人 →「未分配」，未设置优先级 →「无优先级」。
  - **排序**：按截止日/创建时间/标题/优先级，升/降序；空截止日固定排末尾。
- **理由**：全部为客户端计算，数据量 ≤100，无性能压力；纯函数便于单测（章程 II）。共享数据源保证看板/表格始终一致。
- **备选**：后端实现筛选/分组/排序（新增查询参数）被否——任务已全量加载（size=100），服务端查询无收益，反增接口复杂度。

## 决策 6：表格视图与泳道的 UI 组件复用

- **决策**：表格视图复用 shadcn-vue `table`（Table/Header/Body/Row/Cell/Empty）+ `checkbox`（行多选）+ `select`/`dropdown-menu`（筛选/分组/排序控件）+ `badge`（状态/优先级标签）+ `separator`；看板泳道复用既有 `KanbanColumn`/`TaskCard`，在其内部按维度分组渲染，新增薄容器 `KanbanSwimlane`。
- **理由**：所需组件均已安装（来自官方 registry，见 004 数据模型），满足章程 VII"复用优先、官方注册表优先"。本特性**不新增任何自定义基础控件**，`KanbanSwimlane`/`TaskTableView` 仅做组合与布局。
- **备选**：自写表格/多选控件被否——违反章程 VII。

## 决策 7：手机宽度的表格适配

- **决策**：桌面显示完整表格；手机宽度下表格视图降级为"卡片列表"（每任务一张卡片，展示标题、状态、负责人、截止时间），筛选/分组/排序控件折叠进顶部下拉；看板泳道在手机下沿用既有单列 + 列切换器，泳道以分组标题折叠展示。均不引入页面级横向滚动。
- **理由**：满足章程 III"手机宽度无横向滚动"与 FR-022。表格多列在窄屏横向滚动不可接受，卡片式是响应式表格的行业惯例。
- **备选**：表格容器内横向滚动被否——仍属"横向滚动"，且可访问性差；在手机隐藏多数列被否——信息丢失、无法完成批量编辑主流程。
