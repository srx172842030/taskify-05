# 功能规格说明书：第一阶段 — 基础设施建设

**功能分支**：`001-infrastructure-foundation`

**创建日期**：2026-10-16

**状态**：草稿

**输入**：用户描述："第一阶段任务：完成基础设施建设。为后续所有业务功能提供统一的前端界面基础与后端底座。"

## 用户场景与测试（必填）

### 用户故事 1 - 统一的应用外壳与主题（优先级：P1）

终端用户打开应用后，处处看到一致的页面框架：顶部导航栏、主内容区与页脚。在窄屏（移动端）视口下，导航收进抽屉。用户可在亮色、暗色、跟随系统三种外观间切换，其选择在下一次返回时被记住。

**为何此优先级**：应用外壳与主题是后续每个功能所依赖的视觉与导航基础；没有它们，业务页面就没有一致的去处。

**独立测试**：可通过启动应用、确认外壳在桌面与手机宽度下均正常渲染、切换每种主题模式、并在刷新后验证选择被保留来完成，无需任何业务功能。

**验收场景**：

1. **给定** 在桌面视口打开应用，**当** 页面渲染时，**则** 每个页面都一致地显示顶部导航栏、内容区与页脚。
2. **给定** 在窄屏（移动端）视口打开应用，**当** 用户打开导航时，**则** 抽屉菜单提供导航选项。
3. **给定** 用户选择「暗色」主题，**当** 其刷新应用或稍后返回时，**则** 应用保持暗色主题。
4. **给定** 用户选择「跟随系统」，**当** 操作系统主题变化时，**则** 应用外观自动跟随。

---

### 用户故事 2 - 账号注册、登录与登出（优先级：P1）

终端用户使用用户名、密码与图形验证码注册账号，随后用这些凭据与验证码登录。登录后，应用在后续请求中识别该用户，直到其显式登出。

**为何此优先级**：认证是每个后续业务功能的门槛；它必须先于任何受保护的功能存在。

**独立测试**：可通过注册新账号、登录、观察到已认证状态、再登出来完成，无需其他业务功能。

**验收场景**：

1. **给定** 一名新用户，**当** 其以唯一用户名、有效密码与正确验证码提交注册时，**则** 账号被创建且该用户已认证。
2. **给定** 一个已存在的账号，**当** 再次以相同用户名注册时，**则** 显示一致的「冲突」错误且不创建重复账号。
3. **给定** 一名已注册用户，**当** 其以正确凭据与验证码登录时，**则** 其已认证并可访问受保护内容。
4. **给定** 密码错误或验证码无效/过期，**当** 尝试登录时，**则** 以一致的、不泄露细节的错误拒绝。
5. **给定** 一名已认证用户，**当** 其登出时，**则** 其会话失效，后续受保护请求被拒绝。

---

### 用户故事 3 - 面向开发者的统一后端契约（优先级：P1）

开发者为业务能力只需编写服务逻辑与路由；响应格式化、错误处理、入参校验、基于页码的分页、认证与授权都由共享底座提供，无需在每条路由重复实现。

**为何此优先级**：该底座是后续每条业务接口所依赖的单一契约；一致的响应、错误与授权模型是正确性与可维护性中杠杆最高的一环。

**独立测试**：可通过新增一条平凡路由并验证其自动以统一结构返回响应、以一致的参数错误拒绝非法入参、默认拒绝未授权访问、并按页码约定分页来完成，无需编写任何自定义的响应/错误/鉴权代码。

**验收场景**：

1. **给定** 一条业务路由，**当** 其返回成功结果时，**则** 响应使用统一的成功结构。
2. **给定** 参数非法或缺失的请求，**当** 其被处理时，**则** 返回一致的参数错误，且不崩溃、不泄露堆栈。
3. **给定** 无有效认证的请求，**当** 其到达受保护路由时，**则** 以一致的「未认证」错误拒绝。
4. **给定** 已认证但无权限的用户，**当** 其访问受限路由或资源时，**则** 以一致的「无权限」错误拒绝（默认拒绝）。
5. **给定** 一个列表接口，**当** 调用方请求某一页时，**则** 结果按统一的页码约定返回（页码与每页大小）。

---

### 用户故事 4 - 共享组件库与设计画廊（优先级：P2）

开发者构建业务页面时，从共享基础组件集组合而成——按钮、输入框、文本域、选择器、复选框、开关、表单（含校验提示）、对话框、抽屉、下拉菜单、提示消息（toast）、表格、标签页、卡片、徽标、骨架屏、分页——而非自造样式或基础控件。画廊页 `/design`（无独立导航入口，仅通过 URL 直接访问）在亮色与暗色主题下展示每个组件以供参考。

**为何此优先级**：外壳与契约就绪后，组件库是让业务页面能一致、快速组装的关键；它在业务功能之前、外壳之后交付。

**独立测试**：可通过直接访问 `/design` URL 并确认每个组件在亮暗主题下均正确渲染，以及仅用现有组件、不写自定义样式即可组装一个简单页面来完成。

**验收场景**：

1. **给定** 用户直接访问 `/design` URL，**当** 页面渲染时，**则** 每个组件都在亮色与暗色主题下展示。
2. **给定** 开发者构建页面，**当** 其需要任一基础控件时，**则** 已有共享组件可用，且无需自定义样式即可保持一致外观。
3. **给定** 一个带校验规则的表单，**当** 输入非法时，**则** 通过共享表单组件显示校验提示。

---

### 用户故事 5 - 通用状态页（优先级：P2）

终端用户对常见状态看到一致、有意义的页面：404（未找到）、500（服务器错误）、无权限、加载中、空数据——而非空白页或原始错误。

**为何此优先级**：一致的状态处理是用户体验基础的一部分；它可在外壳与组件库之后交付，并被后续所有功能复用。

**独立测试**：可通过直接访问每个状态页（或触发相应状态）并确认每个状态都渲染出一致、品牌化的页面来完成。

**验收场景**：

1. **给定** 用户访问不存在的页面，**当** 路由不存在时，**则** 显示一致的 404 页面。
2. **给定** 意外的服务器故障，**当** 发生时，**则** 显示一致的 500 页面，且不泄露内部细节。
3. **给定** 已认证但无权限的用户，**当** 其到达受保护视图时，**则** 显示一致的无权限页面。
4. **给定** 仍在加载的内容或为空的结果集，**当** 被展示时，**则** 显示一致的加载中与空数据状态。

---

### 用户故事 6 - 参考 CRUD 示例与运维就绪（优先级：P3）

开发者有一份完整的参考实现——一张示例表及其完整 CRUD 接口，用于演示统一契约，作为后续接口的样板。服务还暴露存活与就绪端点、带请求 ID 的结构化日志、安全响应头、CORS 白名单，以及一键启动本地开发环境。

**为何此优先级**：参考示例降低每个后续接口的上手成本；运维就绪（健康检查、日志、安全响应头、本地启动）是系统可可靠运行与部署的前提，但它依赖此前的基础已就位。

**独立测试**：可通过对示例表端到端跑通 CRUD、确认存活/就绪反映真实状态（依赖不可用时就绪失败）、确认请求在日志中带请求 ID、以及一键启动完整本地环境来完成。

**验收场景**：

1. **给定** 示例表，**当** 开发者对其执行增/查/改/删/列表操作时，**则** 每个操作均正常且遵循统一契约（响应结构、校验、分页、错误码）。
2. **给定** 服务正在运行，**当** 调用 `/health` 时，**则** 报告存活状态。
3. **给定** 某个必需依赖（如数据库）不可用，**当** 调用 `/ready` 时，**则** 报告未就绪，而 `/health` 仍报告存活。
4. **给定** 任意入站请求，**当** 其被处理时，**则** 日志结构化并包含将请求与其日志条目关联起来的请求 ID。
5. **给定** 全新检出的代码库，**当** 开发者运行单一启动命令时，**则** 数据库与依赖服务启动，应用可在本地运行。

---

### 边界情况

- 注册已使用的用户名返回一致的冲突错误，且不创建重复账号。
- 使用未知账号或错误密码登录返回一致的、不泄露细节的错误（系统不披露是哪个凭据错了）。
- 无效或过期的验证码以参数错误拒绝，并提示重试。
- 无有效会话的请求被一致拒绝（未认证）。
- 已认证用户访问其无权访问的路由或资源被一致拒绝（无权限），因为授权默认拒绝。
- 格式错误或缺失的请求参数返回一致的参数错误，附带可操作的提示，且不泄露堆栈。
- 启动时某个必需依赖不可用，则就绪失败，而存活仍报告进程存活。
- 超大的结果集由分页约束，而非一次性无界返回。
- 处于「跟随系统」模式时改变操作系统主题，应用外观实时更新。
- 空数据集合渲染空数据状态页，而非损坏或空白页面。

## 需求（必填）

### 功能需求

- **FR-001**：应用必须在每个页面呈现一致的全局布局（顶部导航、主内容区、页脚）。
- **FR-002**：在窄屏（移动端）视口下，导航必须通过抽屉菜单提供。
- **FR-003**：登录弹窗必须作为全局外壳的一部分提供。
- **FR-004**：用户必须能在亮色、暗色、跟随系统三种模式间切换外观。
- **FR-005**：用户的主题选择必须在会话间与页面刷新后保持。
- **FR-006**：在跟随系统模式下，外观必须跟随操作系统或浏览器主题。
- **FR-007**：必须提供共享基础组件集，覆盖：按钮、输入框、文本域、选择器、复选框、开关、表单（含校验提示）、对话框、抽屉、下拉菜单、提示消息（toast）、表格、标签页、卡片、徽标、骨架屏、分页。
- **FR-008**：业务页面必须能由这些组件组合而成，无需自写样式或基础控件。
- **FR-009**：表单组件必须支持校验，并在输入非法时显示校验提示。
- **FR-010**：`/design` 处的设计画廊必须可访问，并在亮色与暗色主题下展示每个组件；画廊不设独立导航入口，仅通过 URL 直接访问。
- **FR-011**：必须存在一致的状态页，覆盖：404、500、无权限、加载中、空数据。
- **FR-012**：每个 API 响应必须使用统一的响应结构。
- **FR-013**：统一的错误码体系必须至少覆盖：参数错误、未认证、无权限、不存在、冲突、限流、服务器错误。
- **FR-014**：业务路由无需自行实现响应格式化或错误处理；由底座提供。
- **FR-015**：请求入参校验必须统一应用，并返回一致的参数错误。
- **FR-016**：分页必须遵循统一的页码约定（页码加每页大小）。
- **FR-017**：用户必须能使用账号、密码与图形验证码注册。
- **FR-018**：用户必须能使用账号、密码与验证码登录，并能登出。
- **FR-019**：会话管理必须是无状态的。
- **FR-020**：授权必须默认拒绝。
- **FR-021**：路由级与资源级权限检查必须通过统一机制提供。
- **FR-022**：必须提供数据库连接与迁移机制。
- **FR-023**：必须提供一张示例表及其完整 CRUD 接口，作为后续接口的参考实现。
- **FR-024**：CORS 白名单必须限制跨域访问。
- **FR-025**：安全响应头必须应用于响应。
- **FR-026**：结构化日志必须包含请求 ID，以关联请求与其日志。
- **FR-027**：必须提供存活端点（`/health`）与就绪端点（`/ready`）。
- **FR-028**：单一命令必须能启动本地开发环境（数据库与依赖服务）。

### 关键实体（若功能涉及数据则包含）

- **用户（User）**：以唯一用户名标识的已注册账号，带有存储的（非明文）密码凭据及创建/更新时间戳。
- **会话（Session）**：已认证用户的无状态、可验证表示（无服务端会话存储）。
- **示例记录（Example Record）**：通用参考实体（例如带名称、描述、属主引用与时间戳的条目），仅用于演示完整 CRUD 模式。

## 成功标准（必填）

### 可度量成果

- **SC-001**：开发者能完全用现有组件组装新页面，无需自写样式或基础控件。
- **SC-002**：用户的主题选择在会话间与刷新后保持，无需重新选择。
- **SC-003**：100% 的业务接口（含参考 CRUD 示例）以统一结构返回响应，并使用一致的错误码。
- **SC-004**：每个非法请求（参数错误、缺少认证、权限不足）返回一致的、可操作的错误，且无堆栈泄露或服务器崩溃。
- **SC-005**：注册与登录流程在正常条件下端到端完成耗时在 3 秒以内。
- **SC-006**：当必需依赖不可用时，就绪端点正确报告未就绪，而存活端点仍报告存活。
- **SC-007**：开发者在全新检出代码库上，用单一命令在 5 分钟内启动完整本地环境（数据库与依赖服务）。
- **SC-008**：设计画廊在亮色与暗色主题下正确渲染每个组件。

## 假设

- 第一阶段不要求邮箱或短信验证；图形验证码是注册与登录的防机器人手段。
- 「账号」指注册时选定的用户名；不要求单独的邮箱地址。
- 技术栈（前端框架、后端语言/框架、数据库）不由本规格指定，将在规划阶段最终确定。
- 「资源级授权」指检查用户对特定记录的访问（例如属主身份或已授予的权限），通过参考 CRUD 示例演示。
- 会话有效期与限流阈值将在规划阶段以安全默认值定义。
- 移动端支持面向手机宽度的响应式 Web；原生应用不在范围内。
- 参考 CRUD 实体是一个纯样板的通用条目，无特定领域的业务含义。
